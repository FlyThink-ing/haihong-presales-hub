## 1. 范围与成功标准

本阶段依据 `requirements-zh-CN.md` v0.18，持续交付可运行的正式应用，不把低保真原型中的内存状态带入正式代码。

已落地的首批范围：

1. 独立账号登录、密码安全摘要、服务端会话、CSRF 防护。
   v0.9：管理员重置后强制本人改密；临时会话仅放行会话状态、改密和退出，业务/下载接口统一拒绝。改密校验当前密码、新旧不同及既有长度要求，完成后撤销全部临时会话并重建会话/CSRF。旧库新增标记默认关闭，不把未重置的旧账号全部强制改密。

3. 客户创建、按当前负责人隔离、部门负责人按直属关系查看、客户转让留痕。
4. 本人提醒与领导指派提醒、统一铃铛入口、工作台摘要、延期原因和原时间留痕。
5. 报价整数金额模型、服务端复算、研发经理—综合部经理—副总经理三级审批状态机、完整内容快照、逐次审批快照、退回自动创建下一版本草稿。
6. 合同预检：客户、项目、报价版本、审批状态、附件明细原含税合计、附件最终优惠价、合同总价、范围、数量、单价、税率和已发布模板版本必须一致。
7. 合同及附件、文件归档的不可覆盖数据结构。
8. 管理员停用/启用账号、重置密码、撤销会话，以及售前单一直属负责人变更历史。
9. 客户项目、联系人、跟进时间线、历史跟进纠正快照和跟进同步提醒。
10. 按既有报价 HTML 单据结构编制和编辑报价；草稿、提交、三级审批、审核人/时间/备注留痕、含税合计与最终优惠价均在同一报价流程展示。
11. 软件调研 A/0 固定为 6 个问答模块（49 题）和 4 张专项清单；草稿可续填，确认版只读，继续修改必须填写原因并生成待重新确认的新版本。
12. 历史客户 Excel 迁移能力曾实现，但用户于 2026-10-19 明确取消正式迁移需求；日常导航已移除，客户和跟进统一由有权限人员自行录入。原兼容代码不作为正式使用入口或验收范围。
13. 已完成调研和已审批报价的可编辑 DOCX；报价只读取副总终审通过时形成的最终审批快照。
14. 本地文件归档：类型/大小/OOXML 签名校验、随机存储名、SHA-256、实体权限下载和上传/生成/下载审计。
15. 岗位职责与售前 SOP 知识库：按岗位、阶段、关键词查询；管理员只增发布版本，所有登录用户可读历史版本；客户、调研和报价页面提供上下文入口。
16. 合同模板门禁：管理员上传、校验、发布 DOCX；原始文件、SHA-256、版本、状态、发布人和时间只增留档，修订、批注、必要锚点缺失或固定正文指纹异常时禁止发布和生成。
17. 调研模板管理：管理员可新建空白草稿或复制已有模板，维护问题模块、问题必填规则、专项清单、字段类型和选项；发布前完整性校验，发布后锁定，历史调研继续绑定原版本。
17. 合同 Word 与归档闭环：只读取副总终审通过的报价快照，服务端锁定附件一、最终优惠价、人民币大写和 10% 年度维护费；草稿人工字段逐项确认后生成不可覆盖原始 Word，外部修改版和最终签订版分别归档。
18. 数据库与文件同批备份：SQLite 在线快照后，以快照中的文件引用为准复制普通附件、合同模板和合同文件，同时纳入合规地图目录；清单验证成功后原子发布，恢复只进入隔离目录。
19. 客户详情八区域汇聚：概览（含项目）、联系人、跟进、提醒、软件调研、全部报价版本、合同、附件与操作日志。主档字段/状态、联系人编辑、跟进纠正和既有业务入口已接通；附件只读汇聚已有业务归档，日志仅本客户最近 200 条。
20. “慕尼黑客户拜访记录”逐行迁移：固定第 2 行表头、完整原字段和不可变来源键，人工选择客户主体/负责人/正式状态/字段及接洽人；合并保护既有非空字段，计划日期和状态原文不生成跟进或提醒，跨批及重复确认幂等。
21. “周汇报”待分类历史来源：逐行逐单元格保存原文、位置、摘要和不可变来源键；人工确认客户、业务类型、日期及内容来源，仅分类或关联来源，不生成跟进、提醒、报价或合同，未税金额永久隔离。

## 2. 为什么使用单体 Node + SQLite

初期只有 5 名售前和少量审批人，主要访问来自公司内网。单体服务可以把鉴权、金额计算和审批事务集中在同一进程与数据库事务内，减少部署组件和权限配置面。SQLite 的 WAL 模式满足当前低并发，数据库文件和附件目录也便于在公司服务器统一备份。

当出现以下任一条件时，再评估迁移 PostgreSQL：并发写入明显增加、多部门同时使用、需要高可用双机、数据库文件超过公司备份窗口，或需要复杂报表副本。当前代码没有为这些未确认场景提前引入分布式组件。

## 3. 正式边界

```text
浏览器 web/
  │  仅发送业务输入和显示服务端结果
  ▼
Express API
  ├─ 身份会话与 CSRF
  ├─ 客户/提醒/调研/文件权限判定
  ├─ SOP 查询、管理员发布与不可覆盖版本历史
  ├─ Excel 解析、映射、历史跟进、拜访及周报来源逐行迁移
  ├─ 报价金额复算与状态机
  ├─ 审批快照 DOCX 生成
  ├─ 合同模板门禁、固定正文指纹与白名单替换
  ├─ 合同一致性预检、DOCX 生成与三类文件归档
  ├─ 在线一致备份、摘要清单与隔离恢复验证
  └─ 操作日志
  ▼
SQLite + 本地文件归档目录
```

浏览器不得通过隐藏按钮或页面路由扩大权限。服务端查询始终带入当前登录账号：

- 售前：只读写 `customers.owner_id = 当前用户` 的客户及关联业务。
- 部门负责人：只访问 `users.manager_id = 当前用户` 的直属售前客户。
- 副总经理：普通客户列表为空；只有待终审或已终审报价上下文提供必要客户资料。
- 管理员：维护用户和基础数据；操作仍写入日志。

SOP 正文以服务端保存的发布版本为准。普通用户及审批角色只有读取权限；只有管理员可以新建文档或发布新版本。发布时保存完整正文、岗位、阶段、关键词、版本号、更新时间、更新说明和发布人；旧版本不更新、不删除，当前版本只通过文档指针切换。初始模板来自本批参考 HTML，但未导入其中的人员姓名、联系方式和个人负责区域。

客户转让在单一事务中更新当前负责人、写入 `customer_transfers` 和 `audit_logs`。后续请求只认当前负责人，因此原负责人立即失去访问权限。

客户详情使用 `GET /api/customers/:id/workspace`：先校验客户权限，再调用正式服务聚合关联内容。副总不能从该接口绕入普通客户；部门负责人按直属范围只读，提醒指派和报价审批沿用原规则。文件下载仍独立复核权限。导入日志不纳入整批 `IMPORT_JOB`，仅显示本客户行级来源，不能由单客户访问权扩大到整个导入批次。

`PATCH /api/customers/:id` 只允许当前售前负责人或管理员维护已有字段，不改负责人归属；来源和类型由管理员独立维护字典。名称不变时允许维护合法同名不同主体主档，改名时仍阻止重名。字段前后值、状态变化、登记时间补录/修改均写审计；历史未知日期保持 NULL，不自动填当天日期，已知日期不得清空。相同主档值重复保存不产生重复变更日志。

v0.9 字典使用原值作为稳定业务键，不预置未经确认的正式选项。系统设置可新增、维护未使用项、启用/停用；已使用项不能改写值或删除，可停用后新增。普通用户只读取启用项；客户已有停用/未知值可原样保留，但正常新增或更改取值必须来自启用项。`used_at` 保留曾使用事实，之后客户改选其他值也不能删除旧项。

管理员候选汇总精确区分原文，不做相似词合并；仅显示原值、当前主档数、导入源行数、字段审计出现次数和启用/停用/待确认状态，不输出客户名称、负责人或整批行数据。既有历史导入不再把类型写死为“新客户/老客户”，未知来源/类型保留原文并汇总候选；确认字典不改写原客户、导入行或审批快照。原有导入行已被旧代码标准化的内容不伪造恢复，后续从原件重新核对来源。

## 4. 提醒规则

- 售前只能为本人负责的客户创建本人提醒。
- 部门负责人只能向直属售前指派该售前名下客户的提醒。
- 副总经理只能向待终审或已终审报价相关客户的当前负责人指派提醒。
- 工作台只返回近期摘要；完整列表和处理动作统一由右上角铃铛打开。
- 领导指派提醒由被指派人完成；延期必须填写原因，并保留 `original_remind_at`。
- 被指派人不能取消领导指派事项；指派人或管理员可说明原因后取消。
- v0.9 无法完成：被指派人说明原因后进入 `UNABLE_PENDING`；原指派人有当前指派权限时可确认关闭、恢复或重新指派，管理员可接管失去权限的指派事项。重新指派只接受客户当前负责人，客户转让仍走独立流程。旧指派人/执行人失去客户权限后，不能从提醒列表、历史或操作接口继续访问；每次前后状态、原时间、内容、原因和实际操作人写入事件历史。
- 统一铃铛显示待确认处理，工作台仅增加待确认摘要。升级会无损迁移旧提醒/事件表的状态约束，并验证外键，不删除旧事件。

## 5. 报价状态机与金额口径

```text
DRAFT
  └─发送审批并生成内容快照→ PENDING_MANAGER
       ├─研发经理通过→ PENDING_VP / GENERAL_MANAGER
       │        ├─综合部经理通过→ PENDING_VP / VP
       │        │        ├─副总经理通过→ APPROVED（锁定）
       │        │        └─副总经理退回→ VP_RETURNED + 新建下一版 DRAFT
       │        └─综合部经理退回→ MANAGER_RETURNED + 新建下一版 DRAFT
       └─研发经理退回→ MANAGER_RETURNED + 新建下一版 DRAFT
```

金额字段均为整数分，税率为基点（`600 = 6%`），数量为千分单位（`1000 = 1`）。每行金额公式：

```text
未税金额分 = round(数量千分单位 × 未税单价分 ÷ 1000)
含税金额分 = round(未税金额分 × (10000 + 税率基点) ÷ 10000)
```

页面提交的行金额如与服务端计算不一致，API 直接拒绝。提交审批时保存完整报价内容 JSON、三级审批流程标识和 SHA-256；每次审批再保存包含当前审批记录的独立快照，快照只增不改。通过时备注默认“通过”，审核人可修改；退回时必须填写原因。系统保存实际审核人、时间和备注，审批记录按权限提供对应版本的报价单入口。退回不会解锁旧快照，而是复制为下一版本草稿。

数据库继续使用 `DRAFT` 作为可编辑状态，页面统一显示为“未发送”，避免把技术状态暴露给业务人员。新建报价前必须维护本人手机和邮箱，用于报价单底部的报价人信息；报价抬头的客户联系人和联系电话由售前人员自行填写，并在发送审批时由服务端校验非空。报价页直接填写客户名称，不展示项目机会选择器，服务端仍保留客户/项目内部关联及权限校验。创建时可暂存 Word（DOCX）附件，报价建立后立即上传；新增及替换报价原文件和报价附件的服务端、预览入口统一只接受真实 DOCX，保留历史 Excel 文件的读取和下载兼容，发送审批时按原机制固定精确版本。

售前直属关系用于客户权限，当前口径统一指向综合部经理。报价一级审核与直属关系解耦：系统只在存在唯一启用研发经理时允许提交和一级审批；二级仍由综合部经理处理，终审由副总经理处理。旧数据若仍把售前关联到研发经理，读取和审批保持兼容，但新建及管理页面默认只提供综合部经理作为直属选择。

v0.18 在不破坏旧报价状态值的前提下增加 `quote_versions.approval_stage`，将同属 `PENDING_VP` 的“待综合部经理审核”和“待副总经理审核”精确区分；旧库原有 `PENDING_VP` 记录按旧流程视为已到副总经理阶段。`users.position_code` 区分研发经理与综合部经理，旧 `MANAGER` 账号兼容为研发经理。新提交版本的不可变内容快照写入三级流程标识，合同和报价 Word 仍兼容升级前已完成的两级历史快照。

报价创建、编辑和查看页沿用用户原 HTML 的同一正式单据结构：公司抬头、居中标题、客户/报价元数据、项目总价表、费用明细表、合计与最终优惠价、条款和报价人信息在一张居中白色报价纸上连续展示；查看页只读。内部附件与当前及历史版本的实际审批记录放在单据之外，避免把内部留痕误导为对客报价正文。宽表只在自身容器横向滚动，单位列为原生下拉预留足够宽度，不扩大整页宽度。已审批报价需要调价时，`POST /api/quote-versions/:id/revise` 要求填写原因，复制当前内容与附件为下一版 `DRAFT`，原版本、终审快照和审批记录保持不可变，新版必须重新走完整三级审批。

## 6. 合同边界与归档

合同模板仅由管理员上传、校验和发布。上传文件保留原始字节和 SHA-256；发布前重新读取原始文件并验证摘要、OOXML 必要结构、变量锚点、未接受修订、批注和固定正文指纹。已发布版本不可覆盖。生成时复制已发布模板，只替换白名单变量和附件一价格表；生成文件重新回读，固定正文片段及所有非正文 OOXML 部件必须与模板一致。

预检输入明确区分 `attachment.subtotalCents` 与 `attachment.finalDiscountCents`：前者必须等于已审批报价的原含税合计，后者必须等于已审批报价最终优惠价；`contractAmountCents` 也必须等于该最终优惠价。存在优惠时三者不强行相等，不分摊、不新增优惠明细行；无优惠时三者自然相等。已有旧库中的 `total_cents` 会在启动时按附件明细原合计和旧最终价回填到两个明确字段，新记录也保持向旧表结构兼容。

合同页面把字段分为三类：

- 系统锁定值：终审报价的产品/附件一明细、原含税合计、最终优惠价、合同总价、人民币大写，以及按最终优惠价除以 10 并四舍五入到分的年度维护费及大写金额。
- 预填并人工确认：甲方完整法定名称、使用权范围、法定代表人、甲方代表、邮编、地址和电话；本期使用权范围必须等于甲方完整法定名称，空签章字段也须逐项确认并留痕。
- 人工录入确认：系统唯一合同编号、签订地点和真实日历日期。地点默认鹤壁，日期按服务器本地日历日生成，不使用 UTC 截断值。

乙方信息、交付周期、付款、验收、知识产权、售后比例、变更和法律条款固定在模板正文中，页面不开放编辑。预检或逐项确认失败会阻止生成。归档类别：

- `SYSTEM_GENERATED`：系统首次生成版；数据库部分唯一索引保证每份合同最多一份，并发失败时清理未入库文件。
- `WORD_EDITED`：用户在 Word 中修改后回传的确认版。
- `FINAL_SIGNED`：最终签字盖章版；后续不得删除。

上传外部版时必须逐项声明是否改变金额、范围、数量、单价或税率。最终版不仅校验本次声明，也检查该合同所有历史 `WORD_EDITED`：历史任一版已声明关键字段变化，就永久阻止该合同标记最终版，并提示回报价创建新版本、重新完成三级审批。原始版、外部修改版和最终签订版均使用随机存储名，保存摘要、上传人、时间和审计记录，不支持覆盖。

## 7. 中国地图

客户经纬度、人员负责区域、客户状态/区域/人员筛选、点位详情和人工选点接口已建立。服务端每次按当前角色及客户负责人重查权限；客户转让后原负责人不能继续查看详情或修改点位。人工选点只保存客户业务坐标并要求填写原因，不采集实时定位或人员轨迹。

## 8. 数据与安全

- 仓库只含 `.env.example` 占位符，不含默认账号、密码、Token、数据库文件或附件。
- 自动化测试每次运行时生成随机测试密码；客户和金额均明确为虚构测试数据。
- API JSON 默认限制 256 KB；Excel 单文件限制 8 MB，合同模板、合同外部版及系统生成 DOCX 限制 20 MB。
- Excel 文件先校验扩展名、MIME、大小和 OOXML ZIP 签名，再解析最多 20 个工作表、每表最多 5000 行和 100 列；公式单元格必须先转换为值。
- 文件实际路径不使用原文件名，而是 `storage/files/<随机 UUID>.<扩展名>`；下载前按导入任务创建人或关联客户/报价权限复核并记录审计。
- 内网生产环境应使用 HTTPS、`HH_SECURE_COOKIE=true`，限制反向代理来源，并对数据库与 `storage/` 做每日备份。

## 9. 内网备份与隔离恢复

### 9.1 配置与调度

`.env` 中配置：

```dotenv
HH_DATABASE_PATH=./data/presales-hub.db
HH_STORAGE_PATH=./storage
HH_BACKUP_PATH=D:\HaihongBackups
HH_BACKUP_HOUR=2
```

`HH_BACKUP_PATH` 应使用内网服务器上仅授权运维访问的独立目录或独立磁盘，不能放在数据库目录、`storage/` 内部，也不能选择包含这些正式目录的父目录。`HH_BACKUP_HOUR` 使用服务器本地时间，允许 0 至 23，默认 2。服务进程对同一数据库和备份目录只保留一个调度器；关停时先停止调度器，再关闭数据库。自动备份失败写入服务错误日志，但不会使业务服务退出。

本期不自动删除任何历史备份。运维人员须监控备份盘剩余空间和增长速度，保留周期及异地副本策略待公司后续确认。

### 9.2 备份批次与原子发布

手工执行升级前备份：

```powershell
npm.cmd run backup -- --reason "升级前手工备份"
```

每次任务先在 `HH_BACKUP_PATH\.partial-<随机值>` 中工作。流程依次为：SQLite 在线 backup API 生成一致快照；从该备份数据库读取 `stored_files`、`contract_templates`、`contract_files` 的 `storage_key`；复制所有引用文件；如存在 `storage/maps/`，完整纳入地图资源；计算数据库和逐文件 SHA-256；执行数据库 `quick_check`、`foreign_key_check`、清单回读和全文件摘要复核。全部成功后才将临时目录原子重命名为 `backup-<时间>-<随机批次>`；任一步失败都清理临时目录。

正式批次包含：

```text
backup-批次号/
  database.sqlite3
  manifest.json
  storage/
    files/...
    contract-templates/...
    contracts/...
    maps/...（存在时）
```

`manifest.json` 只记录清单版本、批次号、生成时间、原因、数据库相对路径和摘要、逐文件相对路径/大小/SHA-256/引用类型及校验结果；不记录源服务器绝对路径，也不复制 `.env`。业务文件本身按既有不可覆盖规则保存，因此备份不要求全站停机；同一进程中的并发备份会被明确拒绝。

### 9.3 离线隔离恢复演练

恢复 CLI 只用于服务器本地、离线、隔离演练，绝不覆盖生产。它会先验证完整 manifest、数据库及文件摘要、数据库可打开、`quick_check` 与 `foreign_key_check`，再把内容恢复到全新隔离目标，完成后再次校验：

```powershell
npm.cmd run backup:restore-drill -- --batch "D:\HaihongBackups\backup-批次号" --target "D:\HaihongRestoreDrills\演练目录"
```

目标目录可以不存在或为空，但不得非空；不得是正式数据库目录、正式 `storage/`、备份根目录、备份批次本身，亦不得是这些路径的父目录或子目录。恢复结果固定为 `目标\data\presales-hub.db` 与 `目标\storage\...`。如需灾难恢复到生产，必须由运维人员在停服、复核演练结果并完成单独变更审批后另行操作；本 CLI 不提供任何覆盖生产的参数。

- 提醒可关联客户档案、联系人、跟进、软件调研、报价版本或合同；创建时验证对象存在、属于同一客户且当前角色可关联。列表只返回当前有权对象的业务名称和页面目标；点击后由目标详情接口再次鉴权，目标失效时不提供可用跳转。

### 17.3 地图和验证边界

- 地图接口返回当前角色可见的售前区域、当前原图 SHA 下有效的客户点、未选点或需重新确认客户、负责人/状态/区域筛选项和有权详情目标。客户点只使用绑定当前原图 SHA 的 0—100 图片坐标；区域标记只使用 manifest 显式锚点，禁止经纬度线性投影或未知区域哈希猜点。普通角色详情进入客户工作区；副总只对待终审或已终审报价相关客户返回报价详情目标，不借地图获得普通客户访问权。
- 客户点位只能由当前负责人或管理员修改，必须提交页面所见底图 SHA-256、该原图上的 0—100 横纵百分比和原因；服务端若发现底图摘要已变化则返回 `MAP_RESOURCE_CHANGED` 并要求刷新重选，数据库和审计保持不变，审计只记录成功写入的前后图片坐标与底图摘要。正式底图未安装、图片真实签名与 JPG/PNG 扩展名不符或其他门禁失败时，人工选点关闭且服务端拒绝写入；页面只显示合规资源占位，不加载第三方边界。
- 自动化和正式 HTTP 仅使用虚构数据、随机凭据、合成 Word 和临时目录；第十四批新增专项覆盖组合筛选、转让失权、Word OOXML、地图资源/点位权限、提醒关联和合同二次确认。浏览器使用虚构售前和副总账号实走筛选、列表/看板、地图占位与筛选、铃铛关联跳转、合同状态二次确认、重复点击及实际 390×844 内容视口；控制台无警告或错误。正式地图原图、生产合同模板视觉复核/发布、真实数据迁移和目标内网服务器部署仍不在本批完成范围。

### 17.4 第十四批独立复核修复（2026-09-03）

- 副总关联提醒只允许当前可读的待终审或已终审报价版本；客户级指派仍按原有审批客户范围处理，不扩展普通客户权限。联系人、跟进、调研和合同由共享关联解析器拒绝，不能通过已知 ID 绕过候选列表。旧提醒仍保留数据库原记录，但返回给当前无权角色的业务目标、关联类型和 ID 为空；事件前后快照同样过滤无权关联字段。

## 18. 第十五批：持久化备份运行状态

- 手工和每日自动备份均先写入运行记录；只有数据库快照、文件清单及摘要校验完成且成功状态落库后，才对外报告成功。状态落库失败时保留“未确认完成”，不得把已生成目录冒充为已确认备份。
- 管理员在系统设置查看最近成功批次及完成时间、同批数据库和文件校验、最近失败安全错误码、每日调度状态和下次计划时间。页面明确说明历史成功不等于当前可恢复，恢复前仍须重新校验清单并完成隔离恢复演练。
- 运行、成功、失败和调度记录保存在 SQLite 中并在重启后保留；重启前未完成记录显示为未确认，不自动改成成功或失败。状态查询只读且仅管理员可见，不返回服务器路径、原始异常、密钥或客户内容。

## 19. 第十六批：通用业务附件

- `business_attachments` 保存业务对象、当前版本和受控删除状态；`business_attachment_versions` 只增保存每次文件版本；`business_attachment_snapshots` 固定保存调研完成或报价提交时引用的精确版本、名称、大小和 SHA-256。实际字节继续由 `stored_files` 的 `BUSINESS_ATTACHMENT` 类别和随机存储键管理。
- 首期对象限定为客户、已保存跟进、调研整体、调研单题和报价版本。合同继续使用原有模板、系统原始版、外部修改版和最终签订版门禁，不允许通用附件绕过合同正文或附件一校验。联系人附件不在本期范围。
- 售前只维护本人当前客户，管理员可维护，部门负责人只读；客户转让后原负责人对当前和历史版本立即失权。副总只可在待终审/已终审报价中读取提交时锁定附件，不能借附件入口读取客户其他资料。
- 上传仅接受 PDF、非宏 DOCX/XLSX/PPTX、PNG 和 JPEG，单文件不超过 20 MB；服务端核对扩展名、MIME、内容签名、OOXML 必要部件、宏/嵌入对象/执行部件、XML 实体、路径穿越、重复条目、CRC 和解压预算。该门禁不等于病毒查杀，页面和文档均明确说明。
- 替换以期望当前版本实现并发保护，新版本不覆盖旧字节；受控删除必须填写原因，仅隐藏当前业务关系，不清除文件或锁定快照。调研完成和报价提交在同一事务内冻结附件；调研新修订及报价退回后的新草稿复制当前关联，但不改写历史快照。
- 页面在客户附件区、每条已保存跟进、调研整体/单题和报价草稿提供上传、替换、历史版本、下载和删除入口。确认版调研、已提交报价及审批页只显示锁定版本。附件操作原位刷新，不关闭或重建正在填写的长表单。
- 旧 `stored_files` 表采用新表复制、删除旧表、改回正式名的方式可重复升级；迁移后复核外键并保留原归档。备份从 `stored_files` 收集全部引用，因此同时覆盖当前、已软删除和被快照引用的附件；隔离恢复回读附件表、快照和字节。

## 20. 长表单草稿防丢

- `surveys`、`quote_versions`、`contracts` 使用独立的 `draft_etag` 和 `draft_saved_at`；旧库启动时幂等补列。

# 主报价单校核规则草案

> 本文件保留为历史规则草案。2026-11-09 起正式报价仅上传 PDF，不再上传 Word 源文件；请同时参阅 `quote-document-review-implementation-zh-CN.md` 顶部的更新说明。

日期：2026-11-02
状态：需求讨论稿，未开发、未启用自动校核

目标是让售前在本地 Word 或 Excel 中方便地制作报价，再由线上平台检查主报价是否符合公司的内容和格式要求，并保留审批与版本记录。规则以现有公司模板为依据，允许表格随业务内容调整。

## 1 已确认的范围

- 只对主报价单进行金额、文字、单位、人民币大写及公司格式校核。
- 附件不参与上述业务校核，不与主报价交叉核对金额，也不要求附件采用统一表格样式。
- 用户已确认主报价与附件通常合在同一文件中；校核需先明确主报价范围，原文件整体保留。
- 用户本轮截图进一步确认：交期、付款方式、开户行、账号、服务文案、报价人姓名、手机和邮箱均属于主报价，全部纳入校核。通常以报价人信息区的邮箱行结束位置作为主报价与附件的主要分界。
- 本地编辑后上传原文件，发现问题后由售前在原文件中修正并重新上传。
- 表格允许增加或删除业务行、调整列宽与行高、合并或拆分单元格、跨页，以及将同一内容区拆成多张表。字段与对应关系需要清楚，不能因排版灵活而丢失必要信息。
- 这份草案不改动应用、配置、数据库、模板原件或现有审批规则。

## 2 当前参考模板

参考文件：`server/templates/quote-template-v1.docx`。该模板来源于用户提供的对客报价 Word。

只读核对时的 SHA-256：`6320fe798ac13d0109db8b3aec6391b2c06223e35a3ad6f038d4b150c4cd39d8`。

当前模板为 A4 纵向，主报价包含公司标识及标题、客户和报价信息、项目总价、项目费用明细、含税金额大写、交期、付款方式、开户行与账号、报价人联系方式。表头底色为 `D9D9D9`，汇总区底色为 `F2F2F2`；不同区域使用的字体与字号按模板分别参考。

模板中现有三张主表只作为参考结构，不设置“必须恰好三张表”的校核条件。输入框的蓝色编辑提示不作为对客文件要求。字体、字号及位置的最终检查还需要文档视觉核对，不能仅凭 XML 结构判定外观合格。

## 3 拟定的校核清单

| 编号 | 检查项 | 拟定规则 |
| --- | --- | --- |
| MAIN-01 | 公司标识 | 主报价有公司 Logo、软件报价单标题及正确的报价单位名称。Logo 允许正常缩放、压缩，不以图片二进制摘要相同作为唯一判断依据。 |
| MAIN-02 | 公司资料 | 公司名称、地址、邮编和电话与公司确认资料一致。开户行、账号为模板中的填充项，正式比对值需使用公司确认资料，不把历史文件中的样例值当成标准。 |
| MAIN-03 | 客户 | 报价客户与系统关联客户核对。简称、历史名称或同名客户无法明确对应时，列为待核对；系统不自动替换客户。 |
| MAIN-04 | 报价信息 | 有报价编号、日期和有效期，文内重复出现的同一信息保持一致。原文件编号与系统编号之间的对应规则暂不新增。 |
| MAIN-05 | 联系信息 | 客户联系人、客户手机保持非必填。报价人姓名、工作电话或手机、邮箱均纳入完整性、格式及对应关系核对，三者应对应本次同一报价人员；不得混淆买卖双方联系人。不能仅因邮箱作为范围识别线索，就跳过邮箱本身的校核。 |
| MAIN-06 | 主表信息 | 按实际填写内容识别项目或型号、单位、数量、未税单价、未税金额、含税金额和备注；费用明细还包含项目与子项的对应关系。允许字段换列、合并表头或拆表，不能仅因列位置不同报错。 |
| MAIN-07 | 金额 | 先识别该报价的计价依据及明示税率，再核对行金额、汇总和优惠。若填写费用明细，其含税合计需与项目总价的含税合计一致；原价及优惠后价格分别核对。无法识别计价依据或税率时列为待核对。 |
| MAIN-08 | 舍入差异 | 区分四舍五入和真实计算错误。含税整行金额反算得到的未税单价乘数量可能存在分位差异，不机械要求所有显示值相乘绝对相等。平台不得静默改写上传文件中的金额，未能解释的差异需人工核对。 |
| MAIN-09 | 优惠 | 存在优惠时核对原合计、优惠及最终报价关系；无优惠时可不展示优惠区。不得把费用明细合计直接与优惠后价格混淆比较。 |
| MAIN-10 | 人民币大写 | 大写金额与最终报价金额一致；没有优惠时对应项目总价。存在多个候选合计而无法确认最终价时，要求人工确定。 |
| MAIN-11 | 数字展示 | 金额按现有要求展示两位小数及千分位。数量、税率、日期、电话和编号按各自字段含义检查，不套用金额格式。 |
| MAIN-12 | 单位 | 检查单位缺失、疑似错字或同一项目的前后不一致。单位是否符合业务含义由人工确认，不把所有项目强制改成同一种单位。 |
| MAIN-13 | 文字 | 对明显错别字、重复字、模板占位符及疑似旧客户信息残留给出定位和建议。客户名、产品名及行业术语优先与已确认资料核对，不自动按通用词典替换。 |
| MAIN-14 | 公司样式 | 公司标识、标题层级、区域字体字号及表头样式以参考模板为依据。允许单元格合理换行、行高变化和内容自然分页，不能要求版面像素完全一致。 |
| MAIN-15 | 商务信息 | 交期、付款方式、开户行和账号均纳入完整性、文字及公司规范校核；收款信息与公司确认资料核对，不能仅检查字段存在。交期、付款方式的具体内容按本报价约定核对，不以模板中的样例条款做全文一致性比较。 |
| MAIN-16 | 主报价尾部文案 | 截图中的服务联系文案属于主报价，检查遗漏、错别字及与公司标准文案的偏差。报价人信息在其后列示，直到邮箱行末都在校核范围内。 |

备注字段不因存在模板列名而变成逐行必填项。校核主表信息时，不把一个合并单元格中明确适用于多行的项目或单位，误判成其余各行缺失。

## 4 结果如何呈现

每项问题提供主报价中的位置、原值、判断依据和修改建议。位置优先使用 Word 的段落或表格单元格、Excel 的工作表和单元格；在未渲染时不编造页码。

- 明确不符合公司规范：如公司名称错误、必要信息缺失、明确的合计错误或大写金额不一致，应修正后送审。
- 需要人工核对：如业务单位、专有名称、计价口径不明确、无法解释的舍入差异或复杂版式。
- 核对通过：只表示已完成的检查项通过。仍有未识别区域或未完成视觉检查时，不给出“全部合规”的结论。

格式建议、业务疑点和明确计算错误应分别列示，不用一条笼统的“检查失败”代替。送审时需保留本版主报价、确认金额和当时的校核结果；修改文件后沿用既有新版本审批口径。

## 5 同文件中的主报价范围

已确认：主报价与附件通常在同一文件中。主报价范围包含截图中的商务信息、服务文案及完整报价人信息，通常截至报价人信息区的邮箱行结束。此后的附件内容不进入金额、文字、单位或格式校核。

建议的范围确认方式，尚未开发：

- 系统结合主报价结构及尾部“报价人—手机或电话—邮箱”信息区识别范围，将邮箱标签及其完整字段所在行末作为主要结束位置。邮箱跨行时应包含完整邮箱字段，不能在中途截断。
- 首次出现的任意邮箱不等于主报价终点：客户信息区、公司页眉或正文中的其他邮箱均不能直接用于截断。应结合字段标签、位置和同一报价人信息区判断。
- 常规布局下标出识别范围供提交人查看，允许调整；范围缺失或有多种解释时，再要求人工确认。不要为了范围确认要求所有报价保持完全相同的分页。
- 邮箱空缺或格式错误时，仍应提示主报价中的相应问题。范围识别与邮箱内容校核分别处理，不能把错误邮箱后的附件一路纳入校核，也不能借用附件中的邮箱冒充主报价结束位置。
- 不能仅因正文出现“见附件”等字样就停止检查。附件标题本身只作为范围识别线索，不校核附件的格式或内容。
- 无法可靠划分时，允许提交人调整主报价的结束位置。Word 以段落或表格边界定位，Excel 以工作表及单元格区域定位；同页或同工作表内也可划分，不强制按整页或整表区分。
- 不要求售前将原文件拆成两份，也不要求在现有文件中新增标记。校核结果与本版文件、确认范围一同保留，重新上传后重新确认范围。
- 范围未明确时显示“主报价范围待确认”，不能宣称主报价已通过校核。

## 6 后续仍需明确的规则

1. 上传原报价中的编号与系统自动编号如何对应。这不影响确认模板中的编号字段存在，但会影响是否执行两者相等的规则。
2. 模板中可填写的开户行和账号采用哪些公司确认值。只从文件样例推导不够作为正式比对标准。

这些边界只影响后续实施。这份文档仅记录讨论和规则草案，不表示校核程序已经开发、部署或验收。
